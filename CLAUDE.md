# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Full-stack alumni engagement platform for ADCET. It is a **monorepo with two independent apps**:

- **Frontend** (repo root, `src/`) — Vite + React 18 + TypeScript SPA.
- **Backend** (`backend/`) — Express + Prisma + PostgreSQL REST API, versioned under `/api/v1`.

The two apps have **separate `package.json` files, separate dependencies, and separate test runners** (Vitest for frontend, Jest for backend). Run their commands from their respective directories.

## Commands

### Frontend (run from repo root)
```bash
npm run dev            # Vite dev server on http://localhost:8080
npm run build          # production build → dist/
npm run lint           # ESLint
npm test               # vitest run (all tests once)
npm run test:watch     # vitest in watch mode
npx vitest run src/path/to/file.test.tsx   # run a single test file
```

### Backend (run from `backend/`)
```bash
npm run dev            # tsx watch, loads .env.development, API on :4000
npm run build          # tsc → dist/
npm run seed           # idempotent dev seed (also places alumni on the map, offline)
npm run geo:backfill   # resolve cities the gazetteer didn't know (uses Nominatim)
npm run db:setup       # migrate (--name init) + seed
npm run db:reset       # reset DB + reseed (destructive)
npm run prisma:migrate # create + apply a dev migration
npm run prisma:studio  # browse data
npm test               # jest --runInBand (all tests)
npx jest src/tests/path/to/file.test.ts    # run a single test file
```

Backend npm scripts inject env via `dotenv -e .env.development`. Running `tsx`/`prisma` directly will **not** load env vars — use the npm scripts. Tests run under `NODE_ENV=test` with `--experimental-vm-modules` (ESM).

Both apps run at once in two terminals: backend on `:4000`, frontend on `:8080` (proxies to the API via `VITE_API_BASE_URL`). Swagger UI is at `http://localhost:4000/api/docs`.

## Backend architecture

**Modular monolith.** Every feature is a self-contained module in `backend/src/modules/<name>/` following a strict layered convention:

```
<name>.routes.ts       # Express router: mounts middleware chain + controllers
<name>.controller.ts   # thin HTTP layer: parse req → call service → send res
<name>.service.ts      # all business logic + Prisma calls live here
<name>.validators.ts   # Zod schemas for request bodies/queries
```

Adding a feature = create the module folder, then add one import + one `apiRouter.use(...)` line in `backend/src/routes/index.ts`. Modules never import each other's routers; shared logic goes in `backend/src/lib/`.

Key conventions:
- **App vs. server vs. worker**: `app.ts` is pure Express wiring (importable in tests, no `listen`); `server.ts` boots it and serves requests; `worker.ts` is a second entrypoint that runs the background jobs and no HTTP server. Don't add business logic to any of the three.
- **Middleware chain order** (see any `*.routes.ts`): `requireAuth` → `requireAdmin`/`requireRoles(...)` → `requireApproved` → `validate(schema, "query"|"body")` → `asyncHandler(ctrl.fn)`. All async controllers must be wrapped in `asyncHandler` so errors reach the global handler.
- **Errors**: throw the helpers from `lib/errors.ts` (`Unauthorized()`, `Forbidden()`, `NotFound()`, etc.) — never `res.status(...).json` for errors. `middlewares/errorHandler.ts` maps `ApiError`, `ZodError`, and Prisma errors (P2002→409, P2025→404) to responses centrally.
- **RBAC**: two roles (`ADMIN`, `ALUMNI`) stored in a **separate `UserRole` table**, not a column on `User`, to prevent privilege escalation. Use `requireRoles(...)` (OR semantics) or `isOwnerOrAdmin(req, ownerId)` from `middlewares/rbac.ts`. `STUDENT` and `RECRUITER` were dropped by migration `20260821090000_drop_student_recruiter_roles` — don't reintroduce them; `ROLE_VALUES` in `config/constants.ts` is the one list every role validator reads.
  - **A role is never read from client input.** `registerSchema` has no `role` field (Zod strips one that arrives, and `register()` hardcodes `ALUMNI`), and `updateProfileSchema`/`updateMeSchema` cannot touch roles or `status`. The only way to hold `ADMIN` is `POST /admin/users/:id/roles` — behind `requireAdmin` — or `seed-admin.ts` bootstrapping the first one. Tests in `tests/integration/auth.routes.test.ts` and `tests/integration/admin.routes.test.ts` pin all of this. Revoking a role also deletes that user's refresh tokens, so a demoted admin cannot mint a fresh token; `req.auth.roles` comes from the access token, so the demotion still takes up to `JWT_ACCESS_TTL` to be felt. An admin may not revoke their own `ADMIN` role — that is a lockout.
- **A partial PATCH must stay partial.** Every optional field in `updateProfileSchema` has three meanings — absent (leave the column alone), `""`/`null` (clear it), a value (store it) — and all three have to survive the parse, because the service hands the parsed object straight to Prisma. A transform that folds `undefined` into `null` (the loose `v == null` does exactly that) turns `PATCH { showLinkedin: false }` into a request that also erases the member's department, batch, birthday and every link on file. Compare against `undefined` strictly, and use the `blank()` helper for the other two cases.
- **Links a user can store are `http(s)` only.** `z.string().url()` is `new URL()` underneath and accepts *any* scheme, so it happily stores `javascript:alert(1)` — which the frontend then renders as an `<a href>` on the public achievement page and in the admin's moderation queue. Every user-supplied link (`Achievement.link`, `Job.applyUrl`, `Event.meetingUrl`, `NewsItem.link`) validates with `httpUrl()` from `lib/urls.ts` instead; `src/lib/urls.ts` mirrors it as `safeExternalUrl()`, which every anchor built from stored data passes its URL through so rows written before the check are inert too. Never use `z.string().url()` for a user-supplied link again.
- **An upload key is not a capability.** `POST /uploads/presign-download` and `DELETE /uploads` take an object key from the request body, so `uploads.service.ts` authorises it: `parseObjectKey()` insists on the `<scope>/<ownerId>/<uuid>-<name>` shape (which also rejects `..` traversal), the private scopes `resume`, `receipt` and `donation-proof` are readable only by their owner, an admin, or — for a résumé — the alumnus who posted the job it was submitted to, and deleting is owner-or-admin always. `LocalStorage` re-checks that a resolved path stays inside the storage root.
- **An upload size limit lives on the server, not in the form.** Bytes go browser → storage, so a form check alone bounds nothing: a caller can skip the page, ask `POST /uploads/presign` for a URL and push whatever they like. `UPLOAD_MAX_BYTES` in `config/constants.ts` gives **every** scope a ceiling; `presignSchema` requires a declared `size` and rejects one over it, `S3Storage.presignUpload` signs `content-length` into the URL (`X-Amz-SignedHeaders`) so the declaration is binding — a body of a different length fails the signature at the bucket — and `POST /uploads/direct` re-checks the buffer it received. Cloudinary has no signable size field, so its hard ceiling is account/upload-preset configuration. `src/lib/uploadLimits.ts` mirrors the table for fail-fast pickers (`backend/src/tests/lib/uploadLimits.test.ts` fails if the two drift), and `src/lib/upload.ts` sends `file.size` with every presign.
- **A payload carries what the page renders, and no more — an email is admin-only.** Two questions decide every `select`: what does this surface actually draw, and who is asking. `person()` / `person(true)` in `lib/selects.ts` is the one shape for "the alumnus attached to a record" (job poster, event organiser, achievement author): identity for a member-facing listing, identity **plus email** when the caller is an admin, chosen per request via `isAdmin(caller)`. Events, jobs and achievements all shipped `createdBy.email` to every approved member while the card drew a name, which turned each listing into a copy of the alumni address book; `tests/integration/person-select.test.ts` reads the `select` the service asked for and pins both halves. Two deliberate exceptions, both consent-by-action and owner-scoped: a job's applicants (`listApplications`) and an event's RSVPs carry the contact details of people who volunteered them to *that* poster. Admin-only routes (`/jobs/pending`, `/admin/*`, the ledgers, the exports) keep everything — say so with `person(true)` rather than by inlining a select.
  - **`GET /profiles/:userId` answers with a page, not a row.** `memberViewSelect` in `profiles.service.ts` is who someone is, where they studied and what they do now — plus their links, chapter, experience, education and skills. `phone`, `birthDay`/`birthMonth` and `rollNumber` are details an alumnus gave the *college*, not the network; `admissionYear` is derived and `locationId` is map plumbing. The owner asking about themselves, and any admin, still get the full row through `profileInclude`. `showLinkedin` is applied on top for everyone else.
- **CSV exports neutralise spreadsheet formulas.** Report columns carry names and companies members typed themselves, and the file opens on an admin's machine, so `csvCell` (backend `admin.service.ts`, mirrored by `src/lib/csv.ts`) prefixes a `'` to any cell starting with `= + - @` before quoting.
- **Pluggable storage**: `backend/src/storage/` has a `StorageService` interface with `LocalStorage` / `S3Storage` (MinIO in dev, S3 in prod) / `CloudinaryStorage` adapters, selected by `STORAGE_DRIVER` env var. Never call a provider SDK directly from modules — go through the storage service. Uploads are always browser → storage; `presignUpload()` returns either a `PUT` URL (S3 family) or `method: "POST"` + signed multipart `fields` (Cloudinary), and the frontend's `src/lib/upload.ts` handles both. `CloudinaryStorage` derives resource type and public id from the object key's extension; `src/lib/storage.ts` mirrors that mapping to build delivery URLs client-side — keep the two in sync.
- **Departments**: the 12 official ADCET department names live in `config/constants.ts` (`DEPARTMENTS`), mirrored verbatim by `src/lib/departments.ts` on the frontend — `src/tests/lib/departments.test.ts` fails if the two drift. Every **write** path (sign-up, profile PATCH, event, job) validates with `departmentSchema` / `optionalDepartmentSchema` from `lib/departments.ts`, so the column can never hold free text again; **read** filters use the lenient `departmentFilterSchema` so a stale value narrows results instead of 400ing. Frontend dropdowns render `DEPARTMENTS` (or `DEPARTMENT_FILTER_OPTIONS`, which prepends `"All"` — always strip `"All"` before sending). Migration `20260803093000_rename_departments` rewrote the old abbreviations and free-text spellings; don't reintroduce them.
- **Events and jobs target a *list* of departments**: `Event.departments` and `Job.departments` are `String[]`, validated by `departmentListSchema` (which de-dupes and drops the legacy `"All"` sentinel). **An empty array means everyone** — the same thing the old nullable `department` column meant by NULL. Within a list the departments OR together (`department: { in: [...] }`); read filters use `departments: { has: x }`, so postings open to all are deliberately *excluded* from a department-specific filter — it asks "aimed at X", not "visible to X". The UI is `src/components/DepartmentMultiSelect.tsx` (checkboxes), used by both create forms and both admin forms.
- **Sign-up proves the applicant studied here.** Nothing on an account used to say so — an admin approving one had a name, a batch and a department, every one of them typed by the applicant, with a LinkedIn URL standing in as a weak proxy. Sign-up now requires a **library card, marksheet, leaving certificate or degree certificate**, and `AdminUserDetailPage` renders it inline above everything else on the review screen, because it is the only claim there the office can actually check.
  - **The upload happens before the account exists**, which is the whole difficulty: the document is collected at the end of step 2, before the email is verified, so there is no user to own the object and no session to authorise it. `POST /auth/register/identity-document` is therefore the **one** endpoint in the application that takes bytes anonymously. Four things bound it: `authLimiter`; the MIME type checked against `IDENTITY_DOCUMENT_MIME_TYPES` rather than trusted; the size checked against the bytes actually received (there is no declared size to trust); and `jobs/pendingUploadCleanup.ts`, which deletes what no sign-up claimed after `PENDING_UPLOAD_RETENTION_HOURS`. Raw body, not JSON — a phone photo of a marksheet base64s well past the 1 MB body limit.
  - **`PendingIdentityDocument` is the bridge, and `claimedAt` makes it single-use.** The endpoint answers with the row's **id, never the key**, so a guessed id is worth one claim and nothing else. `register()` exchanges it via a conditional `updateMany` on `claimedAt` — the database arbitrates two sign-ups racing for one document — and writes the key onto `Profile.identityDocumentKey`. The claim happens *after* the OTP is spent and *before* the user is created: a failed create leaves the document claimed and unusable, which is the right way round, since an unclaimed id surviving a failure could be replayed onto a different account.
  - **`identity` is a private upload scope with its own rule.** The key was minted before its owner had an account, so its `<ownerId>` segment is the upload's id and the usual owner match cannot work; `authorizeRead` resolves the real owner through `Profile.identityDocumentKey` instead. Admins and the alumnus themselves, nobody else — a marksheet carries a roll number, a date of birth and a photograph.
  - **LinkedIn is optional.** It was mandatory as a stand-in for "is this person really an alumnus", which the document now answers properly, and requiring it turned away alumni who don't use LinkedIn. It left `REQUIRED_PROFILE_FIELDS` with it, so `profileComplete` no longer gates on it.
- **Sign-up requires a full profile**: `registerSchema` makes department, degree, graduation year, birthday, phone, city, current company and current role all mandatory alongside name/email/password. Two things are deliberately *not* collected: the **admission year** (derived via `admissionYearFor(degree, graduationYear)` — B.E./B.Tech is 4 years, M.E./M.Tech is 2, from `DEGREES` in `config/constants.ts`) and the **birth year** (only `birthDay` + `birthMonth`, for birthday wishes). `DegreeType` has just `BE` and `ME`; PHD/DIPLOMA were dropped.
- **There is no social sign-in.** Google, LinkedIn and GitHub were removed with migration `20260909120000_manual_donations_and_drop_oauth`, which dropped the `OAuthAccount` table; the provider registry, the `/auth/oauth/*` routes, `loginWithOAuth` and the `/auth/callback` page are all gone, and a test in `tests/integration/auth.routes.test.ts` asserts those routes 404. Email + password is the only way in. Don't reintroduce a provider: an SSO account proves someone owns an address, which is not what approval is for, and it was the only thing that ever created an account with an empty profile. `User.passwordHash` stays nullable for legacy rows, and login/reset/change-password all refuse an account without one.
  - **`/complete-profile` survives as the safety net.** `registerSchema` collects every mandatory field, so a form sign-up is complete on creation — but accounts that predate that rule (and any the office imports) are not. `publicUser` reports `profileComplete` (from `lib/profileCompletion.ts`), and `ProtectedRoute` redirects anyone incomplete (admins excepted) to `/complete-profile`, which posts to `POST /auth/complete-profile`. That endpoint reuses the very same `requiredProfileFields` object as `registerSchema`, so the second door cannot let a field through that the first demands; a test asserts `REQUIRED_PROFILE_FIELDS` and that object stay in step. Completing a profile never changes approval status.
- **Emails are case-insensitive identities**: every email field flows through `emailSchema` in `auth.validators.ts`, which trims and lowercases at the validator boundary. The DB has both a `User.email` unique constraint and a `lower(email)` unique index, and `register` catches P2002 as a 409 — the pre-flight lookup alone can't survive two concurrent sign-ups.
- **Donations are paid off-portal and verified by hand — there is no payment gateway.** Razorpay was removed (the college would not carry the fee) along with its order/verify/webhook endpoints, `lib/razorpay.ts`, the `RAZORPAY_*` env vars and the `razorpay*` columns. Everything in `modules/donations/` now follows from one fact: **nothing a donor tells us about a payment is evidence.**
  - **Where the money is paid lives in settings, not env.** `donationUpiId`, `donationPayeeName`, `donationQrKey`, `donationBankDetails` and `donationInstructions` are `lib/settings.ts` entries the alumni office edits at `/admin/settings`, and `GET /donations/payment-details` (member-gated — it is where money goes, not public copy) serves them with a `configured` flag that is false until at least one way to pay is filled in. `DonationsPage` then says "not published yet" instead of drawing an empty QR frame, and `submit()` refuses to take a claim it could not have been paid against.
  - **The lifecycle is submit → verify → receipt.** `POST /donations` files what the donor says they paid — amount, `reference` (the UTR), `paymentMethod` (`UPI` or `BANK_TRANSFER`, the only two ways the office publishes; `DONATION_PAYMENT_METHODS` in `config/constants.ts`, mirrored by `src/lib/donations.ts` and pinned by `tests/lib/donations.test.ts`), `paidAt`, an optional screenshot — as `PLEDGED`, and emails an acknowledgement that says *in as many words* that it is not a receipt. `POST /donations/:id/approve` (admin) is the **only** thing that turns a claim into money: it stamps `verifiedAt`/`verifiedById`, mints the receipt number, generates the PDF and emails it. `POST /donations/:id/reject` (admin, reason required) archives it. A member may `POST /donations/:id/withdraw` their own submission, but only while `PLEDGED` — withdrawal stops at the decision, as with collaboration requests.
  - **A reference identifies one transaction, so `Donation.reference` is unique.** The service pre-checks it for a decent 409 message; the constraint is what actually stops a re-claim, since two concurrent submits both pass the lookup. It is normalised at the validator boundary (upper-cased, inner whitespace stripped) so `"abc 123"` and `"ABC123"` cannot both exist.
  - **The admin decides from the whole submission, not a table row.** `DonationReviewDialog` (`src/components/admin/DonationReviewDialog.tsx`) opens from both the pending queue and any ledger row and shows everything the alumnus filled in — the reference to search the statement for (copyable, in monospace), amount, method, date paid, campaign, message, the anonymous flag, the donor and their email — with the proof **rendered inline**, fetched through `POST /uploads/presign-download` because `donation-proof` is a private scope with no public URL, and the `DonationLedgerEntry` trail as a history. It is the only reader of that table, which is what keeps the append-only writes from being write-only. Verify and Reject live in the dialog as well as on the queue strip; a decided row still opens, because the office has to be able to answer a donor who writes in months later. The ledger table itself carries only what a row needs to be *found* — donor, cause, amount, reference, receipt no., status, date — and no file buttons: the dialog is where files are opened.
  - **The ledger is paged; its totals are not.** `GET /donations` takes `page`/`pageSize` like every other list, and the header cards and per-campaign breakdown come from `GET /donations/stats` instead of being summed from the rows on screen — a total derived from a page would say "received on page 3". Both take the same filters, so the cards and the table always agree about what is being looked at. `donorCount` is the one figure that needs raw SQL (`COUNT(DISTINCT)` has no Prisma equivalent, and the alternatives return a row per donor just to measure the array); `pendingCount` deliberately ignores the status filter, so an admin reconciling `RECEIVED` still sees submissions piling up behind them.
  - **One frontend type for a donation row.** `AdminDonation` in `src/lib/donations.ts` is what the ledger, the queue and the review dialog all read; it lists exactly the fields something draws, so `Donation` carrying more (`currency`, `archivedAt`, `campaignId`) is a deliberate difference and adding one back means deciding where it appears. `STATUS_LABELS`, `STATUS_TONE` (inline text) and `STATUS_BADGE` (chips) live beside it rather than being re-declared per surface.
  - **A proof key is not a capability.** `proofKey` must start `donation-proof/<callerId>/` or `submit()` 400s — otherwise a donor could attach another member's bank screenshot to their own donation and hand it to the verifying admin. `donation-proof` is a private upload scope (owner-or-admin); `donation-qr` is deliberately public.
  - **Rejected means archived, then gone.** `reject()` sets `archivedAt`, and `jobs/donationPurge.ts` (in `worker.ts`, daily, behind a `JobLease`) deletes the row and its screenshot once that is older than `DONATION_ARCHIVE_RETENTION_DAYS` (30). It sweeps `REJECTED` rows only, and deletes the file *before* the row so a failure retries next sweep rather than stranding the object. `approve()` clears `archivedAt` and the reason, so an admin can undo a wrong rejection and the purge no longer sees it. **Rejection is only available from `PLEDGED`**: a receipted gift is money in the account and a PDF in somebody's inbox, and archiving it would schedule that record for deletion.
- **Donations are earmarked to a campaign**: `POST /donations` takes an optional `campaignId`, recorded on the `Donation` so the alumni office can see what each gift was given for (admin ledger has a "Given for" column, a campaign filter, and a per-campaign received breakdown). **Omitting it is valid** — that's a general-fund gift. `resolveCampaign()` in `donations.service.ts` rejects archived, not-yet-open and closed campaigns *before* the row is written, so money is never pinned to a wound-up campaign; the donor-facing picker only lists ones currently open. Five campaigns ship in `seed.ts`.
  - **The public honour roll is derived, never curated.** `GET /donations/public/top-donors` (anonymous, `limit` capped at 24, 5-minute in-process cache dropped by `invalidateTopDonors()` whenever a gift settles or an admin moves its status) sums each donor's gifts and feeds `TopDonorsStrip` on the landing page. Three filters make it publishable and must stay: `status: "RECEIVED"` (a `PLEDGED` row is an unverified claim any member can file in ten seconds — counting it would sell a place on the landing page for free, and a `REJECTED` one is a claim the office already refused), `isAnonymous: false` (the donor's own veto, applied retroactively because the total is recomputed every time), and `user: { status: "APPROVED" }`. Names, photos and batch come from `User`/`Profile` live, **not** from the frozen `donorName` snapshot the receipt uses, which is what makes the roll follow the alumni data. The section renders nothing at all when the list is empty.
- **Admin-tunable settings**: `backend/src/lib/settings.ts` holds a typed registry (key → Zod schema + default + label/description) and is the source of truth for **defaults**; the `AppSetting` table stores only overrides, so a missing row is normal and adding a setting needs no migration. Read with `getSetting(key)`, write with `setSettings({...}, adminId)`; a stored value that fails its schema is logged and falls back to the default. Exposed as `GET/PATCH /admin/settings`, which also returns `meta` so the admin UI renders labels without duplicating copy. Don't reach for `SiteSection` for settings — it survives only as a key/value store for the achievement authority recipients (`ACHIEVEMENT_RECIPIENTS_KEY`, edited from the admin Settings page) and its read endpoint is public.
- **Feed post quota**: members may publish `feedPostsPerMonth` (default 10) posts per **calendar month**, resetting on the 1st — a fixed reset day is far easier to explain than a rolling window. Admins are exempt. `feed.service.ts` exposes `getPostQuota()` (served at `GET /feed/quota`); `create` rejects with 429 when spent and returns the decremented `quota` alongside the post so the composer can toast "N posts left" without a second round trip.
  - **Usage lives in `PostQuotaUsage`, never in a count of `Post` rows.** The counter is append-only and keyed `(userId, "YYYY-MM")`: publishing spends the slot for that month *permanently*, so deleting the post does not hand it back and the cap can't be farmed by posting and deleting in a loop. `create` writes the post and the increment in one `$transaction` — a published post always costs a slot, and a slot is never spent without a post. Nothing in `remove` may touch the counter; a test asserts that.
- **Alumni Collaboration is a request board, not a scheduler** (`modules/collaboration/`): alumni offer to do something *for* the college — run a placement drive, conduct a workshop — and the office approves or rejects. Approving creates no `Event`, no `Job` and no calendar entry; it means "yes, let's talk", after which the office reaches the alumnus on the contact details captured in the request. Four rules:
  - **One table, one `type` discriminator.** Every kind shares the submit → PENDING → decision lifecycle, so `CollaborationRequest` holds the shared columns plus each kind's own nullable ones, and `collaboration.validators.ts` — *not* the schema — decides which are mandatory, via `z.discriminatedUnion("type", ...)`. Cross-field checks hang off the union with `.superRefine`, never off a member: `.refine()` turns a member into a `ZodEffects` that `discriminatedUnion` refuses. Adding the next kind is an enum value, a union member, its optional columns, and one entry in `COLLABORATION_KINDS`.
  - **`OTHER` is the catch-all, and has no columns of its own.** Anything an alumnus offers that is neither a drive nor a workshop goes through it, so what makes such a request actionable is the description — which is why `otherSchema` is the one member of the union that promotes `description` from optional to **required** — and `startDate` doubles as its preferred date rather than earning a second column meaning the same thing. If one sort of request keeps arriving through it, that is the signal to give it a named kind. `COLLABORATION_TYPES` lives in `config/constants.ts` (not in the validators, which now re-export it) because the admin's pending counters read it too; the frontend mirrors it in `src/lib/collaboration.ts`, where each kind now also carries its own `titlePlaceholder` and `description` copy so `CollaborationPage` renders the form without branching on `type`.
  - **Nothing here is public, at any status.** The whole router is `requireAuth + requireApproved`; a member reads and writes only their own requests (the service forces `userId` into the `where` for non-admins), and every decision route is `requireAdmin`. Approval never widens the audience — an approved drive is a private arrangement, not community content, which is the opposite of how achievements work.
  - **The frontend is written once and driven by `COLLABORATION_KINDS`** in `src/lib/collaboration.ts`: that record supplies each kind's slug, page copy and detail rows, and `CollaborationPage` / `CollaborationAdminPage` each take a `type` prop. The member page is a form on the left and the **Actions** panel on the right (their own requests with a status tag); the admin page is the same request rendered through the very same `RequestDetails` block, so the two sides cannot drift. Both sidebars render the kinds through `SidebarNavGroup`.
  - **Withdrawal stops at the decision.** A member may delete their own request only while it is `PENDING`; once decided, the row carries the reason they were told and deleting it would erase that. Admins may remove any request.
- **Newsroom is the only CMS**: the alumni office publishes two content types from `/admin/newsroom` (`src/pages/admin/NewsroomPage.tsx`) — `NewsItem` (public `/news` + `/dashboard/news`) and `Newsletter` (public `/newsletters`). Both live in `modules/content/` behind public GETs and admin-only writes; the frontend types and query factories are in `src/lib/newsroom.ts`. Two consequences:
  - **A newsletter carries its own cover.** `Newsletter.coverKey` is page 1 of `fileKey`, rasterised **in the admin's browser** by `src/lib/pdfCover.ts` when the PDF is picked, then uploaded under the `newsletter-cover` scope. No server-side rasteriser is required, and `pdfjs-dist` is reached only through that file's dynamic `import()` so it never lands in the public bundle. Both keys resolve through `assetUrl()` in `src/lib/storage.ts`, which passes `public/` paths straight through — that is how the two seeded editions (PDFs committed under `public/NewsLetter/`) coexist with uploaded ones.
  - **The old "Site Content" editor is gone**, along with `ResourceItem` and the `/dashboard/about|contact|mentorship|resources` pages: the public pages own that copy now. `src/lib/siteContent.ts` is down to fixed intro text for the two surviving in-portal pages (news, support). Don't reintroduce a section-copy editor.
- **Gallery is admin-managed** (`modules/gallery/`): `GalleryAlbum` (one event) has many `GalleryPhoto`. Public `GET /gallery/albums` is `optionalAuth` and returns published albums only — an admin passing `includeUnpublished=true` also sees drafts, which is why the controller re-checks `isAdmin(req)` instead of trusting the query. Photos are uploaded browser → storage under the `gallery` scope, then their keys are posted in one batch (`POST /gallery/albums/:id/photos`, appended after the existing `sortOrder`). Deleting an album or photo also deletes the stored object, except for keys starting with `/` — those are the seeded albums committed under `public/gallery/` and must never be deleted. Frontend types + mutations live in `src/lib/gallery.ts`; admin UI is `src/pages/admin/GalleryAdminPage.tsx`.
- **Directory search is name + company only**: `nameAndCompanyMatch()` in `alumni.service.ts` splits the query into words and ANDs them (so a full name narrows), each word ORing over first name, last name and employer. Department and graduation year are deliberately **not** searchable — they are multi-select filters instead, arriving as comma-separated `departments` / `graduationYears` query params (`csv()` in `alumni.validators.ts`) and applied as `{ in: [...] }`. The shared UI is `src/components/MultiSelectFilter.tsx`.
  - **The default order is per viewer, and hides nobody.** `GET /alumni` sorts by relevance to the caller — their own department first, then outwards from their own batch (own year, then the seniors, then the juniors) — so the same query opens on a different first page for every member. It is expressed as *bands*: `relevanceBands()` splits the result set into `{ where, orderBy }` slices that are plain Prisma queries on the `[department, graduationYear]` index (ordering `graduationYear` desc from the viewer's year *is* "my batch, then my seniors"), and `searchByRelevance` counts every band, then walks them until the page is full. There is no raw SQL and no ranking expression. A band is a slice, never a filter: the counts add up to the same `total` the plain sorts report, and `sort=batch` / `sort=name` give the viewer-independent orders. The basis comes from the caller's own profile (`viewerFor`), never from the query string, and is echoed back as `relevance` so the page can say what it did.
  - **A directory row carries only what the card draws.** `cardSelect` in `alumni.service.ts` is an explicit `select` — before it, `findMany` returned the whole `Profile` (phone, birthday, every link) and the frontend simply didn't render most of it. Adding a field to the card means adding it here on purpose. The joined user is narrowed to id + names; a listing never carries an email.
  - **`Profile.showLinkedin` is the owner's veto on their LinkedIn link** (default `true` — every approved member could already read the column, so defaulting to `false` would have removed nothing and left the feature dead). It gates the icon on the directory card *and* `GET /profiles/:userId`; honouring it on one surface only would make the switch a decoration. The owner and `GET /profiles/me` always see their own link, the flag itself never ships to anyone else, and the URL stays on file when it is switched off. The switch lives with the link inputs in `ProfilePage`.
- **Chapter cards show a city photograph**, not a colour: `chapterImage()` in `src/lib/chapters.ts` maps slug/city → a file in `public/Chapters/` (both "bangalore" and "bengaluru" resolve). `Chapter.accent` survives only as the fallback header for a chapter with no photograph — there is deliberately no colour picker in the admin form any more.
- **The alumni map is DB-driven and clustered** (`modules/geo/`). Five rules hold it together:
  - **Coordinates live in the database, one row per city.** `GeoLocation` (unique `slug` = normalised `city|country`) is referenced by `Profile.locationId`. Nothing geocodes per request, and nothing geocodes per alumnus: 50,000 alumni in 200 cities cost 200 lookups. `GET /geo/public/map` (and its authenticated twin `GET /geo/map`, same payload) answers with three indexed aggregates plus one read of the small `GeoLocation` table, behind a 60-second in-process cache — call `invalidateMapCache()` after anything that rewrites coordinates.
  - **Resolution is gazetteer-first and never blocks a write.** `lib/geocode.ts` tries an existing row, then the offline `config/gazetteer.ts` (aliases included, so "Bangalore"/"Bengaluru" converge on one point and one row), and only then Nominatim — and only when the caller passes `allowRemote`, which `jobs/geoBackfill.ts` does and request paths never do. A city the gazetteer doesn't know leaves `locationId` null; the nightly backfill (or `npm run geo:backfill`) places it later, works per distinct city rather than per profile, and is idempotent. Adding a city to the gazetteer is an optimisation, never a requirement.
  - **City precision is the floor, by construction.** Only city + country are ever sent to a geocoder, only a centroid comes back, and `roundCoord` coarsens it to `GEO_PRECISION` (3 dp). There is no column that could hold a street address, and signing in buys no extra precision — a test asserts the anonymous and member payloads match.
  - **The map page is only the map.** No stat tiles, city index or country breakdown on `/alumni-map` or `/dashboard/geomap` — headcounts are on the markers, and the reporting lives in the admin Geo Map (`AdminGeoMapPage`). A test asserts the metrics stay off the public page.
  - **Clustering is supercluster, not markers-per-record.** `buildClusterIndex()` in `src/lib/geo.ts` weights clusters by the **summed headcount** via its `map`/`reduce` pair, so a marker reads "287 alumni" rather than supercluster's own `point_count` ("4 cities"). `src/components/public/AlumniMap.tsx` is only the Leaflet rendering half — it redraws the visible clusters on move/zoom and flies to `getClusterExpansionZoom()` on click. Don't reintroduce `leaflet.markercluster` or a hardcoded city→coordinate table (both were removed; the old `src/lib/city-coords.ts` is gone).
- **Content has a lifetime, and deleting it must not delete the numbers.** `lib/retention.ts` is the single definition of when a job leaves the board and when a job or event is deleted; `jobs.service.ts`, `events` reporting and `jobs/contentRetention.ts` all read their predicate from it, so the listing and the sweep cannot disagree about what "expired" means. `now` is always a parameter, never `new Date()` inside, so the boundaries are testable at an exact instant.
  - **A job is visible for 30 days and deleted at 45** (`JOB_RETENTION` in `config/constants.ts`). The gap is not slack: the board hides an expired posting while its author can still open it and read the applications, which is when they are shortlisting. `Job.expiresAt` is the override — set it and both dates move by the same amount, because the grace is *derived* (`RETENTION_DAYS - VISIBLE_DAYS`) rather than written as a third constant. Admins are never filtered; `myPostedJobs` is not filtered either, and instead returns `isExpired`/`expiresOn`/`purgesOn` so `MyJobPostsPage` can say when a posting goes rather than letting it vanish. `apply()` refuses an expired posting, so a stale link is not a way round the board.
  - **An event is deleted six months after it *finishes*** (`EVENT_RETENTION_MONTHS`) — `endsAt` where it declared one, `startsAt` otherwise, so a week-long reunion is not swept a week early. Upcoming events are never swept, however old the row is. `monthsBefore()` clamps a short month by hand; `setUTCMonth` alone rolls 31 August − 6 months into 3 March and would sweep a batch of events early.
  - **The archive is what survives.** Each purge writes an `ArchivedContent` row carrying exactly the dimensions reporting slices by — month (the *source* row's `createdAt`, not the purge date), status, `departments` verbatim, `isClosed`, and the application/RSVP counts read **before** the cascade removes them. `analytics.overview()` adds archived rows to the job and event totals, `adminInsights()` `UNION ALL`s them into the monthly trend queries and adds their frozen RSVP counts, and the jobs/events CSV exports append them with an `Archived` column. Without this the college's headline numbers would fall every night as content aged out.
  - **Four rules make the deletion safe**, and `tests/jobs/contentRetention.db.test.ts` proves them against a real Postgres: the archive row and the delete are **one transaction** (separately, a crash loses a month or double-counts it); `(kind, sourceId)` is **unique**, so a retried sweep cannot re-archive; **storage objects go first** and their failure keeps the row for the next sweep — deleting the row first would strand the attachment and every applicant's résumé in the bucket with nothing left naming them; and it works **one row at a time** with a `MAX_PER_RUN` cap, so a bad row costs that row rather than the sweep. `resumeCleanup` deletes the same résumé keys on its own longer clock and tolerates them already being gone.
- **Background jobs run in `worker.ts`, never in the web process** (`npm run worker` in dev, `npm run start:worker` in prod). `backend/src/jobs/` exports only `run*` functions — event reminders, résumé cleanup, geo backfill, token cleanup, rejected-donation purge, job/event retention, abandoned-upload cleanup — and `worker.ts` owns the schedule. They used to start in `server.ts`, which meant *every* API replica ran every tick: three replicas sent every alumnus three copies of each event reminder and tripled the request rate at Nominatim, whose policy allows one per second. Two rules:
  - **Run one worker.** Every tick still claims a `JobLease` first, so a rolling deploy that briefly overlaps two workers — or an accidental scale-up — skips the tick instead of duplicating it.
  - **It is a lease, not a lock.** `pg_try_advisory_lock` belongs to a *connection* and Prisma pools them, so the unlock can land on a different connection than the lock did; the transaction-scoped variant would hold a transaction open for a whole mail run. And a worker that is SIGKILLed mid-run cannot release anything, so the claim expires on its own (`leaseMs`, sized to exceed the job's worst-case runtime) and the next tick takes over. The claim is one `INSERT … ON CONFLICT DO UPDATE … WHERE` statement, which is what makes it atomic without a transaction — `lib/jobLease.ts`, tested against a real Postgres in CI.
- **Email**: `lib/mailer.ts` + `lib/email-templates.ts` (branded HTML). Day-only columns (`driveDate`, `occurredOn`, …) hold a calendar day stored at midnight UTC, so they render through `formatDay()` in `lib/dates.ts` — formatting them in the process's own zone shows the previous day west of UTC and mails an alumnus a date they never picked. Events/jobs send department-targeted emails; event emails contain token-signed RSVP links handled by the **public** `GET /events/:id/email-rsvp` endpoint (JWT in query params, no session).
- **Chapters** (`modules/chapters/`): regional alumni communities (Pune/Mumbai/Bangalore/Global seeded by migration + `DEFAULT_CHAPTERS` in `config/constants.ts`). Five rules the code depends on:
  - **Members read, admins write — with one exception.** `/dashboard/chapters` (`src/pages/ChaptersPage.tsx`) shows alumni the same chapter cards the admin sees and lets them click through to a chapter's roster; the only thing a member may change there is **their own answer to an invitation addressed to them** (the `MyInvitations` panel, from `GET /chapters/invitations/me` + `POST /chapters/invitations/:id/respond`). There is still no join, invite, edit, remove or archive control on it: every *other* mutating chapter route is `requireAdmin` and a test posts to each one as an approved member expecting 403, while the respond route re-checks the invitation's own `userId` and 403s anyone else's. `GET /chapters/:id/members` is the one route that widened: it is now `requireAuth + requireApproved`, and the controller passes `includeEmail: isAdmin(req)` so the email column is *not selected* for members — matching the alumni directory, which never returns one. Admins still manage everything under `/admin/chapters`.
  - **Display order is `Chapter.sortOrder`, not the alphabet** — the office wants Pune (1), Mumbai (2), Bangalore (3), Global (4). `list()` orders by `[isActive desc, sortOrder asc, name asc]` and every surface (public landing section, `/dashboard/chapters`, `/admin/chapters`) renders that one list without re-sorting, so the order is fixed in a single place. Chapters created later default to `sortOrder: 100` and fall in after the seeded four. `FALLBACK_CHAPTERS` in `src/lib/chapters.ts` must stay in the same order — it is what the public page renders when the API is unreachable. The **Global chapter** is the catch-all for alumni outside the three hubs; its `city` is deliberately NULL (it is not a place), so only its slug resolves `chapterImage()`, and the card omits the location line. It is created by migration `20260813051933_chapter_order_and_global`, not by `seed.ts`, because a deployed server only runs migrations plus `seed-admin.ts`.
  - **Invite-only membership** — there is deliberately no self-service join anywhere. An admin creates a `ChapterInvitation`; the alumnus becomes a member only when they accept. There are **two doors onto the same answer**, and both must keep working: the signed one-click links in the invitation email (public `GET /chapters/invitations/email-respond`, same token pattern as event RSVPs), and the pending-invitation panel on `/dashboard/chapters` (`POST /chapters/invitations/:id/respond`, session-authenticated). The portal door exists because an undelivered email used to strand an invitation forever — the invitee had a notification telling them to check an inbox and no way to act. Inviting must never grant membership — a test asserts this — so an admin still cannot add anyone unilaterally.
  - **One chapter per member** — membership is a single `Profile.chapterId`, not a join table, so accepting an invite repoints it and moves them out of any previous chapter (the email and confirm dialog say so). `updateProfileSchema` deliberately omits `chapterId` so it can't be set via a profile PATCH.
  - **Delete only while empty** — `DELETE /chapters/:id` succeeds only with zero members and zero events; otherwise it 409s and tells the admin to archive instead (`isActive: false`), which keeps members, events and history but hides the chapter and closes it to new invitations.
  - **Targeting is AND** — `Event.chapterId` and `Event.departments` are both optional narrowing filters on notifications, intersected (`{ department: { in: [...] }, chapterId }` on the profile relation). Chapter never affects event *visibility*, only who gets emailed. `jobs/eventReminders.ts` mirrors the same clause so reminders reach the same audience.

Prisma schema and `seed.ts` live in `backend/prisma/`. After changing `schema.prisma`, run `npm run prisma:migrate`.

## Frontend architecture

- **Routing** (`src/App.tsx`): all routes declared in one file. Three tiers:
  - Public routes (landing, login, static pages). `/login` and `/register` both render `AuthPage`, which picks its panel from `location.pathname` and mounts **only that one** — never both, at any breakpoint (a CSS-hidden second form would still expose duplicate email/password fields to screen readers and password managers). Public CTAs must match their wording: "Join Network" / "Get Started" → `/register`, "Sign In" → `/login`; `src/pages/auth-page.test.tsx` asserts this.
  - **The landing page runs in a fixed order**, asserted by `src/components/public/LandingSections.test.tsx`: founder → `LeadershipRow` (Secretary left, Joint Secretary right, driven by the ordered `LEADERSHIP` array in `src/lib/public-content.ts`) → director → `AlumniNetworkMessage` → board → chapters. The welcome message is long, so `AlumniNetworkMessage` renders only its **first** paragraph under `line-clamp-6` behind a Read more toggle. Clamp that one paragraph, never the container: `line-clamp` counts lines inside a single block, so clamping a wrapper of several `<p>`s cuts at a paragraph boundary instead of at six lines.
  - **Testimonials are one landing-page section with an overflow page behind it.** `TestimonialCard` (portrait left, name/batch/designation under it, quote right) is shared by the auto-advancing carousel in `TestimonialsSection` and by `/testimonials`, which renders the same card with `full`. The carousel shows an excerpt from `excerptOf()` — a word-boundary cut with a literal `...`, not a CSS line clamp, so every card is the same height — and the quote links through to the full page. `/testimonials` is deliberately **absent from the public nav**: the carousel is its only entry point, and a test asserts no such nav link exists.
  - `/complete-profile` — logged-in but outside `DashboardLayout`, so there is no nav to escape into until onboarding is done.
  - `/dashboard/*` — wrapped in `<ProtectedRoute>` (any logged-in role) → `<DashboardLayout>` → `<AccountStatusGate>` (blocks non-approved users).
  - `/admin/*` — wrapped in `<ProtectedRoute roles={["ADMIN"]}>` → `<AdminLayout>`.
  - **An achievement has two detail surfaces, and in-portal links must use the portal one.** `/dashboard/achievements/:id` (`AchievementDetailPage`) is a plain content block inside `DashboardLayout` — nav, sidebar and theme come from the layout, Back walks history and falls back to `/dashboard/achievements`, and it reads the authenticated `GET /achievements/:id` so an author can open their own *pending* submission. `/achievements/:id` (`PublicAchievementPage`) is the shareable twin for readers with no session: its own slim header, "Back to home", a sign-up CTA, and the anonymous `GET /achievements/public/:id` (published only). Both render `src/components/AchievementArticle.tsx`, so the achievement itself can't drift between them; only the surroundings differ. Cards in `AchievementsPage` link to the portal route, the landing page and the achievement emails link to the public one — pointing a portal card at `/achievements/:id` is the bug that made a click appear to leave the application, and `src/pages/AchievementDetailPage.test.tsx` now pins each side.
  - **An admin can record somebody else's achievement, and the byline follows the achiever.** `POST /achievements/admin` (its own route, so the fields that say *whose* it is sit behind `requireAdmin` rather than being ignored on the shared one) takes exactly one of `userId` — the entry is filed under that member and appears on their achievements, `achieverName` stays null — or `achieverName`, for someone who never registered, where the row is owned by the filing admin and that name is the byline. Admin entries land **APPROVED and silent**: the admin is the moderation step, and the office adds historical entries in batches. `achieverOf()` in `src/lib/achievements.ts` is what every surface bylines with; reading `user` alone bylines an office-recorded entry "Admin User". `AchievementFormDialog` is the single form both pages use.
  - **The byline's LinkedIn is resolved by the API, never assembled by the page.** `withByline()` decides it once: for an entry about somebody off the portal (`achieverName` set) only the admin-typed `achieverLinkedinUrl` can apply — falling through to the author's profile would print the *filing admin's* LinkedIn under a stranger's name — and for an entry about its own author the profile link applies **only if their `showLinkedin` switch allows it**, which also overrides a link an admin typed for them: "don't show my LinkedIn" cannot mean "unless an admin adds it for me". The public endpoints select `achieverName` but never the link, exactly as the directory does. `linkedinUrl` arrives `null` when there is none — the ordinary case, not an error — and every surface renders the icon only when `achieverLinkedin()` returns something, so a missing link shows nothing at all rather than a dead icon or a message.
- **Every route is code-split, and every chunk is prefetched.** `App.tsx` declares routes through `route(path, () => import(...))`, which files the import thunk in `src/lib/routePreload.ts` under the path it serves; use it rather than `lazy()` directly or the new page will never be prefetched. Three things then keep the split from being *felt*, and all three are load-bearing:
  - **The suspense boundary lives inside the layout.** `RouteContent` (rendered where `DashboardLayout` and `AdminLayout` used to render `<Outlet />`) owns a boundary around the outlet, so a page whose chunk is in flight suspends only the content pane. The single app-level boundary that used to wrap the whole route table meant React replaced the nav and sidebar with a blank fallback and rebuilt them — which is what read as the page reloading. `src/components/RouteContent.test.tsx` asserts the shell stays mounted.
  - **`BrowserRouter` runs navigation in a transition** (`future={{ v7_startTransition: true }}`). Because the pane's boundary is already mounted, React keeps the current page painted until the next chunk resolves instead of showing a fallback at all.
  - **Chunks are warmed before the click** — `preloadGroup` on idle once a layout mounts (a member in the dashboard shell will navigate inside it), and `preloadRoute` on hover/focus of any `NavLink`. Both are idempotent and swallow failures; the real navigation retries the import and surfaces it properly.
- **API client** (`src/lib/api.ts`): the single typed gateway to the backend. Framework-agnostic (no React imports). Persists JWTs in `localStorage` under `adcet.tokens`, auto-attaches the bearer token, and on 401 **transparently refreshes once and retries**. On hard auth failure it clears tokens and dispatches an `adcet:auth-expired` event that `AuthContext` listens for to sign out. Add new endpoints here rather than calling `fetch` from components.
- **State**: `AuthContext` (auth/session) and `ThemeContext` (5 themes + dark mode, persisted per-user in DB) in `src/contexts/`. Server state uses TanStack Query; there is no global store like Redux.
- **UI**: shadcn/ui components in `src/components/ui/` (generated — see `components.json`; regenerate rather than hand-editing). Styling is Tailwind. `@/` path alias maps to `src/`.
